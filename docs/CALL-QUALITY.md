# Качество звонков: что сделано и как проверять

Этот документ описывает механизмы адаптации (js/callquality.js, js/webrtc.js, js/group-call.js) и протокол слепого теста для людей.
Реальных измерений в плохих сетях здесь нет: их нужно собрать по протоколу ниже на настоящих устройствах.

## Что реализовано

| Область | Механизм |
|---|---|
| Opus | В SDP, уходящий собеседнику, добавляются useinbandfec=1, usedtx=1, minptime=10, maxaveragebitrate по классу сети (good 64 / fair 40 / poor 24 кбит/с), stereo=0. Одна функция `tuneOpusSdp`, идемпотентная; если Opus нет или правка не удалась, SDP уходит как был. |
| Видеокодеки | `setCodecPreferences`: iOS -> H.264; Android -> H.264 (аппаратный), затем VP8/VP9; десктоп 4+ ядер -> VP9; иначе VP8. Список кодеков сохраняется целиком (откат на любой общий кодек). |
| Адаптация | Каждые 2 с getStats -> потери, RTT, джиттер, availableOutgoingBitrate, зависания. Лестница: 100% -> 60% -> 35% (масштаб /2, 24 fps) -> 18% (15 fps) -> только аудио. Вниз: 2 плохих тика подряд; аудио-режим: потери >15% или RTT >800 мс 6 с подряд. Вверх: 16 с хорошо на шаг, из аудио-режима 30 с. Обе стороны видят плашку. |
| Группа | Видео-бюджет делится между получателями (mesh), больше 4 видео-получателей -> видео выключается, остаётся звук; предел участников 6, меньше при слабом канале/устройстве. |
| Установка | Несколько TURN из /ice упорядочены по измеренному RTT (замер при открытии экрана звонка, не чаще раза в 10 мин); подогрев сбора кандидатов при открытии экрана звонка; ICE restart сразу при смене сети (`online`, `navigator.connection`), не ждём таймауты; таймаут ожидания кандидатов при ICE restart 1.8 с. |
| Приватность | Настройки -> «Скрывать мой IP в звонках»: iceTransportPolicy relay, только TURN. Минус: ниже качество, больше задержка; нет TURN -> соединение не установится (IP не раскрывается). По умолчанию выключено. |
| Отчёт | Настройки -> «Отчёт о качестве звонка» (по умолчанию выключено). После звонка тост вроде «Звук отличный. Задержка 40 мс, потери 0%.» и экспорт JSON. Данные только на устройстве. |

## Синтетический замер

`node tools/call-bench.js [--seconds 20] [--video] [--relay] [--out result.json]` поднимает локальный сервер и два Chromium с fake-медиа, делает звонок по ссылке и печатает JSON (битрейт, fps, джиттер, потери, кодек, RTT, тип пути). Это loopback: он показывает, что звонок поднимается, кодеки и цикл адаптации работают. Реальную сеть он не моделирует.

## Протокол слепого теста

Цель: сравнить Ether с конкурентом (или двумя сборками Ether) без предвзятости.

Участники: 2 тестера на звонок, минимум 5 пар на сценарий. Перед тестом каждая пара случайно (монетка) решает, в каком порядке идут приложения A и B; тот, кто оценивает, не знает, какое приложение какое (скрыть логотип/название, звонок запускает помощник).

Сценарии:
1. Хороший Wi-Fi с обеих сторон.
2. 4G в движении (транспорт или ходьба), 10 минут.
3. 3G / слабый сигнал (или ограничение канала до ~384 кбит/с через сетевой эмулятор).
4. Потери 5% (tc netem loss 5% или Network Link Conditioner).
5. Потери 15%.
6. Переключение Wi-Fi -> LTE посреди звонка (выключить Wi-Fi на 30-й секунде).

Для каждого звонка по 3 минуты (4G: 10 минут), одинаковый сценарий речи (чтение фиксированного текста по очереди, потом свободный разговор).

Метрики:
- MOS 1-5 (ACR): 5 отлично, 4 хорошо, 3 нормально, 2 плохо, 1 ужасно. Каждый оценивает слышимое качество после звонка.
- Задержка рот-ухо: один говорит «раз» и одновременно хлопает рядом с записывающим телефоном, второй записывает свой экран/звук; задержка измеряется по двум дорожкам в аудиоредакторе (или секундомер-метод: оба хлопают по очереди, разность считается по записи).
- Время установки: от нажатия «Позвонить» до первого слышимого звука у вызываемого (по записи экрана, секундомер).
- Батарея: заряд до и после 10 минут звонка при одинаковой яркости экрана, выключенных остальных приложениях; разность в процентах (повторить 3 раза, взять медиану).
- Для Ether дополнительно: включить «Отчёт о качестве звонка» и приложить JSON.
