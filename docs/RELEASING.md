# Выпуск подписанного релиза

Цель: чтобы приложение (и любой желающий) могло проверить, что раздаваемые файлы выпущены владельцем, а service worker не принял подменённое обновление. Приватный ключ подписи **никогда** не попадает в репозиторий, CI, облако или чат.

Границы: подпись не защищает первую установку и не спасёт, если украден сам приватный ключ; встроенная проверка в приложении — сигнал, а не доказательство (подробно `docs/THREAT-MODEL.md`, п. 3.3).

## Что есть в репозитории

| Файл | Назначение |
|---|---|
| `js/release-key.js` | публичный ключ `window.RELEASE_PUBKEY`; сейчас `null` (заглушка, подпись не настроена, приложение работает как раньше и честно пишет «не настроено») |
| `tools/release-keygen.js` | генерация пары ECDSA P-256; приватный ключ пишет только вне репозитория |
| `tools/release-manifest.js` | `release-manifest.json`: SHA-256 каждого раздаваемого файла |
| `tools/release-sign.js` | подпись манифеста → `release-manifest.sig.json` |
| `tools/release-verify.js` | проверка подписи и каждого файла (код 1 при расхождении) |
| `js/integrity.js` | проверка в приложении (Настройки → Безопасность) |
| `sw.js` | новая версия активируется только при верной подписи, если ключ настроен |

Раздаваемые файлы: `index.html`, `sw.js`, `manifest.webmanifest`, `config.js`, `servers.json` (если есть), всё в `js/`, `css/`, `fonts/`, `icons/`, `sounds/`, `.well-known/`. Тесты, docs, сервер, tools в манифест не входят. На GitHub Pages положите пустой файл `.nojekyll` в корень, чтобы `.well-known/` раздавался.

## Шаги владельца (один раз)

1. На доверенной офлайн-машине (чистая система, без чужих расширений):
   `node tools/release-keygen.js --private ~/secrets/ether-release.pem`
   Команда создаст приватный ключ (права 0600) и перепишет `js/release-key.js` публичной частью.
2. Сделайте минимум две резервные копии `ether-release.pem` на носителях офлайн (зашифрованная флешка, бумажная копия PEM в сейфе). Потеря ключа = невозможность выпускать обновления с проверкой (придётся менять ключ вручную, см. ниже); утечка = любой может выпустить «подписанное» обновление.
3. Закоммитьте только `js/release-key.js` (публичный ключ). Приватный ключ не коммитьте и не кладите в секреты CI.
4. Также заполните реальный контакт в `SECURITY.md` и `.well-known/security.txt` (там заглушки TODO).

## Шаги на каждый релиз

1. Закончите правки, соберите: `node tools/build-bundles.js`, `node tools/csp-hash.js`, поднимите `VERSION`/`CACHE_VERSION` как обычно.
2. `node tools/release-manifest.js`
3. Подпишите (офлайн или на доверенной машине): `node tools/release-sign.js --key ~/secrets/ether-release.pem` (или `ETHER_RELEASE_KEY=<путь|PEM>`).
4. Проверьте: `node tools/release-verify.js` (должно быть «OK: подпись верна»).
5. Закоммитьте `release-manifest.json` и `release-manifest.sig.json` вместе с файлами релиза; ничего не меняйте после подписи (любое изменение файла = новый манифест = новая подпись).
6. Деплой (как обычно, по команде «мержь и деплой»).

CI (`.github/workflows/ci.yml`) на каждый push доказывает, что конвейер работает (временная пара ключей), и падает, если закоммиченный манифест устарел относительно файлов; если закоммичена и подпись, то проверяет её открытым ключом из `js/release-key.js`.

Важно: пока в `js/release-key.js` настоящий ключ, service worker отклонит любое обновление без свежего манифеста и подписи. Забыли подписать — пользователи остаются на старой версии и видят «Обновление не прошло проверку подписи».

## Сменить ключ

Service worker закрепляет ключ при первой установке с ним и отклоняет другой ключ или его отсутствие (иначе подмену ключа можно было бы сделать тихо). Смена ключа: объявите её отдельным каналом, пользователи должны переустановить приложение (удалить PWA/данные сайта и открыть заново) или вручную очистить кэш `ether-meta`. Автоматической ротации нет — это осознанное ограничение.

## Как проверить чужому человеку

`git clone`, затем `node tools/release-verify.js --pub js/release-key.js` против опубликованного дерева, а `js/release-key.js` сверьте с ключом, объявленным владельцем независимо (например, в нескольких каналах). Сравнивайте именно keyId (первая строка комментария в `js/release-key.js` и вывод `release-sign.js`).
