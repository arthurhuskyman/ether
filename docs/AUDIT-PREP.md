# Подготовка к независимому аудиту

Аудит пока **не проводился и не оплачивался**; этот документ собран, чтобы его можно было заказать (или провести силами сообщества) без раскопок в коде. Модель угроз — `docs/THREAT-MODEL.md`, политика сообщений — `SECURITY.md`.

## 1. Рекомендуемая область аудита

Приоритет 1 (криптография и протокол): Double Ratchet и prekey-пакеты, конверты v1/v2 (AAD), аутентификация P2P-канала, сертификаты устройств и перенос на новое устройство, шифрование в покое, подпись релизов.
Приоритет 2 (поверхность атаки): разбор недоверенных входов (расшифрованные payload, приглашения, QR, ссылки, файловые метаданные), service worker и его кэш, CSP, сервер сигнализации (авторизация по claim-токену, лимиты, ящик, push).
Приоритет 3: WebRTC-логика звонков, групповые звонки/комнаты, поиск по номеру/email.
Вне области: UI-скины и CSS, переводы, vendor-библиотеки (кроме проверки версий).

## 3. Как запускать

```
cd tests && npm ci && cd ../signaling-server && npm ci && cd ..
cd tests && node --test --test-concurrency=2 --test-timeout=180000 *.test.js     # клиентские тесты
cd signaling-server && npm test                                                    # серверные тесты
node tools/build-bundles.js --check && node tools/csp-hash.js --check && node tools/validate-languages.js
node tools/coverage.js client | server                                             # пороги 90% строк / 80% ветвлений
```

Fuzz/устойчивость (детерминированные seed, секунды): `cd tests && node --test fix80-fuzz-codec.test.js fix80-fuzz-ratchet.test.js fix80-fuzz-payloads.test.js`. Общие генераторы — `tests/fuzz-helpers.js` (mulberry32). Чтобы увеличить охват, поменяйте seed или число итераций в тесте; находка должна воспроизводиться по seed. Для более глубокого fuzz рекомендуем подключить внешний фаззер (например jazzer.js) к тем же функциям: `SignalingCodec.decode`, `Ratchet.decrypt`, `applyIncomingPayload`, `handleFilePayload`.

Подписанные релизы: `tests/release-signing.test.js`, `tests/release-integrity.test.js`.

## 4. Тестовые векторы

Известные ответы (KAT) для ML-KEM-768: `tests/vectors/mlkem768-kat.json` (сид, хэш открытого ключа, шифртекст, общий секрет, implicit rejection) и проверка SHA-384 вшитого `js/vendor/ml-kem768.js`. Для ratchet/HKDF/конвертов фиксированных KAT **пока нет**: тесты проверяют круговую передачу и мутации (`tests/ratchet.test.js`, `fix77-ratchet`, `ratchet-pq` — матрица со старым клиентом `tests/fixtures/ratchet-v79-legacy.js`, `ratchet-app`, `fix80-fuzz-ratchet`, серверные `test-ratchet-envelope.js`, `test-prekeys*.js`). Нужно добавить KAT и формальную спецификацию — первый пункт для аудитора; отдельно просим проверить гибрид (порядок входов KDF, связывание заголовка) и выбор вшитой реализации ML-KEM.

## 5. Известные ограничения

Из `docs/AUDIT-V76.md` (построчный внутренний аудит V.76.1.0; статусы там на дату аудита — «не исправлено», многое исправлено в V.77–V.79, актуальность сверяйте по `git log`). Крупные темы: сервер (раздел 1), WebRTC/крипто (2), клиентские модули (3–5), SW и index.html (6), доступность/контраст/RTL в скинах (7).

Дополнительно, найденное при подготовке V.80 (см. также `docs/THREAT-MODEL.md`):
1. (V.80, в основном закрыто) Подсказки `rc`/`ac`/`cp` по-прежнему вне AEAD, но уровень «липкий» после проверенного конверта, а биты возможностей и начальный заголовок аутентифицированы (AAD v3 + HKDF); остаётся первый обмен до любого проверенного конверта и сокрытие prekey-пакета (см. `docs/THREAT-MODEL.md`, «Остаточные риски»).
2. Фиксированные векторы есть только для ML-KEM-768 (`tests/vectors/mlkem768-kat.json`, получены независимой реализацией OpenSSL, проверяются `tests/ratchet-pq.test.js`); для ratchet/HKDF/конвертов KAT и формальной спецификации по-прежнему нет.
3. Подпись релиза защищает установку обновлений и даёт внешнюю сверку, но не первую установку; смена ключа подписи не автоматизирована (осознанно, чтобы её нельзя было сделать тихо).
4. Метаданные не скрываются (кто, кому, когда, размер); нет сокрытия адресов серверов.
5. Удаление и исчезающие сообщения у собеседника — просьба клиенту, не гарантия.
6. Мониторинга уязвимостей зависимостей нет, воспроизводимая сборка «бит в бит» не оформлена (бандлы детерминированы, CI проверяет актуальность).
7. Для fuzz покрыты основные парсеры; полностью не покрыты WebRTC SDP-обработка и групповые звонки.

## 6. Вопросы аудиторам

1. Корректна ли схема старта сессии без подписи prekey при отсутствии пакета (старт от долговременных ключей): какие свойства теряются (forward secrecy первых сообщений, KCI)?
2. Достаточна ли привязка DTLS-отпечатков (`linkauth.js`) против активного сервера; нет ли reflection/relay-атак на HMAC-доказательство?
3. Оценка выбора KDF-параметров для PIN (PBKDF2-SHA256, 250 000 итераций, PIN ≥ 6 цифр) и формата `enc1:`.
4. Модель повторов/пропусков в ratchet (`MAX_SKIP`, `MAX_SKIPPED_STORED`, история ключей собеседника): DoS по памяти и «отравление» состояния.
5. Сертификаты устройств и перенос аккаунта: возможность отката списка (seq), подмены отозванных устройств, гонки при привязке.
6. Service worker как точка доверия: достаточна ли схема «закреплённый ключ + подпись манифеста + хэши» для безопасных обновлений; что упущено для сценария скомпрометированного хостинга.
7. CSP на GitHub Pages (через meta): что не получается защитить без HTTP-заголовков (frame-ancestors, report-to) и как это компенсировать.
8. Устойчивость сервера к перебору id/claim-токенов, enumeration присутствия, обходу лимитов.
9. Безопасность функции поиска по номеру/email (солёный HMAC, перебор) с точки зрения приватности.
10. Разбор недоверенных payload: пропущенные классы входов, прототипное загрязнение, ReDoS.
